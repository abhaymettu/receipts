\title{Claims Without Receipts:\\How Often Coding Agents' Reports Go Unbacked,\\and Why Receipt Rules Cannot Tell}
\author{Abhay Mettu}
\date{November 2026}

\begin{abstract}
At the end of each turn a coding agent tells its user what it did: ``tests pass'', ``I updated
\texttt{config.py}'', ``committed as \texttt{a41c9e2}''. Most users believe the report and move on, so a claim
the agent never checked is found only later. We built \texttt{receipts}, a checker that tests each claim
against the agent's own tool calls in the same session, and used it to ask how often those statements are not
backed, and whether the deterministic receipt rules that several recent Stop-hook tools use can find the ones
that are not. From 2,301 Claude Code and Codex sessions on one
developer's machine we drew 400 reported turns uniformly at random and labelled the 2,082 claims in them with
two isolated model raters plus a third adjudicator on the held-out split, audited by the author. 13.3\% of
claims are not backed by the agent's receipts (95\% CI 11.3 to 15.4, session bootstrap). Outright contradictions
are rare (5 of 2,082); the failure is claiming without current evidence. Unbacked claims concentrate in ``it
works / it's fixed'' (36.8\%) and ``tests pass'' (22.5\%) claims and rise with session length (5.1\% in sessions
of 1 to 9 tool calls, 13 to 20\% in longer ones). Our second finding is negative: deterministic receipt rules,
even after a 15-round climb on a development split, agree with careful readers at chance on held-out turns
(verdict $\kappa \approx 0$, end-to-end flag precision 0.083 and recall 0.153 with model-assisted claim
extraction). A model that reads the receipts does far better (Sonnet: flag precision 0.557, recall 0.315,
verdict $\kappa$ 0.52). We release the checker, which runs as a Claude Code Stop hook in either mode, with the
benchmark pipeline.
\end{abstract}

\section{Question}

Developers who hand work to coding agents read the agent's end-of-turn report far more often than they read its
tool calls. When the report says the tests pass, most users move on. Two questions follow.

\begin{enumerate}
\item \textbf{Prevalence.} In ordinary use, what share of an agent's claims about its own work are not backed by
the receipts it left in the session: the commands it ran, their outputs, the files it wrote? Which kinds of
claims, and which sessions?
\item \textbf{Detection.} Several open-source Stop hooks released in 2026 (proof-of-done~\citep{boyko2026proofofdone},
honestly~\citep{honestly2026}, groundtruth~\citep{groundtruth2026}) parse the transcript, find claims with
patterns, and require a matching successful command after the last edit. They report precision on
author-written fixtures or unvalidated counts. Does that mechanism agree with careful readers on real sessions?
\end{enumerate}

We take no position on intent. A claim is ``not backed'' when the agent's own record does not support it at the
moment it was made, whether because nothing checked it, the check came before a later edit, or the check
failed. We do not say the agent lied.

A small pilot preceded this study: 5 sessions and 324 claims, which suggested roughly 1 in 9 claims were
unbacked. It is kept in the repository under \texttt{archive/v0/}. This paper replaces it with a sampled,
labelled and validated measurement.

\section{Data and sampling}

\paragraph{Frame.} The population is every main-thread Claude Code transcript and every Codex rollout on one
developer's machine written before 2026-11-01 10:00 UTC (\texttt{bench/frame.py}). Of 5,922 candidate
transcripts, we drop 2,443 with no tool calls or no report, 116 test-harness sandboxes that replay other
sessions, 1,054 that work on private projects the owner keeps out of public work, and 8 after the cutoff. The
private-project rule looks at what a session works on (working directory, typed prompts, tool calls, reports)
rather than injected memory, which names those projects in nearly every transcript. 2,301 sessions remain:
2,267 Claude Code and 34 Codex, with 7,169 reported turns and 88,379 tool calls. Most are the developer's
autonomous ``lanes'' (long unattended agent runs) and orchestration sessions; few are short interactive edits.

\paragraph{Sample.} A reported turn is a turn that ends in agent text. We drew 400 reported turns uniformly
(seed 20261101) and split them by a hash of the session into a development split (225 turns, used for tuning)
and a test split (175 turns, used only for the reported validity numbers). Claims within a session are not
independent, so every interval in this paper comes from a bootstrap that resamples sessions (2,000 resamples,
seed 7).

\paragraph{Dossiers.} For each sampled turn, \texttt{bench/label.py} writes a dossier: the user prompt, the
report, and every tool call in the session up to that report, oldest first, with its command or target, the
files it wrote, whether it errored, and a clipped copy of its output. Calls from the reporting turn are marked.

\section{Labelling protocol and agreement}

\paragraph{Rubric.} Raters follow \texttt{receipts/rubric.md}. A claim is a sentence, bullet or table row in which
the agent asserts, as done or true now, something about its own work in this session that a tool receipt could
back or refute. Claims fall in eight families: \texttt{tests}, \texttt{build}, \texttt{files}, \texttt{git},
\texttt{ship} (deploys, installs, pushes to services), \texttt{ran} (``I ran X''), \texttt{verified}
(``I checked that...''), and \texttt{works} (``it works'', ``fixed''). Plans, hedges and findings read off tool
output are out of scope. Each claim gets a verdict: \emph{supported}, \emph{contradicted} (a receipt shows the
opposite), or \emph{unbacked} (no receipt shows it, or the only one predates a later change to the code it
covers, which we call stale). ``Not backed'' means contradicted or unbacked.

\paragraph{Raters.} Labels are per turn, not per extracted claim: a rater lists every claim in the report with a
verdict, so any extractor can be scored against the same labels and recall is measurable. Raters are Opus 5.5
sessions run through \texttt{claude -p}, isolated from the machine's settings, hooks, memory and MCP servers,
with read-only tools over one dossier each. Rater A labelled all 400 turns. Rater B labelled the 175 test turns
independently.

\paragraph{Agreement.} On the test split A listed 890 claims and B 880, of which 786 matched (claim-set F1
0.888). On matched claims they agreed on the verdict 94.8\% of the time (Cohen's $\kappa$ 0.739) and on the
binary not-backed flag with $\kappa$ 0.757 (\texttt{results/validity\_agreement.json}).

\paragraph{Gold labels for the test split.} Claims both raters listed with the same verdict (745) go straight to
gold. The remaining 239 disputes (a claim only one rater listed, or differing verdicts) went to a third Opus 5.5
adjudicator, which read the same dossier plus both raters' notes; it ruled 205 to be claims and 34 not. The author
audited 40 rulings drawn at random (seed 11), agreed with 37, and reversed 3, all of which were findings read
off tool output that the rubric puts out of scope (\texttt{results/adjudication\_audit.json}). Gold on the test
split holds 950 claims. On the development split, rater A's labels are gold.

\paragraph{Matching.} A system claim matches a gold claim when their sentences overlap: one contains the other,
or token Jaccard similarity is at least 0.5. Pairs are made greedily, same family first.

\section{Checkers compared}

All checkers read the same session record. They differ in how they find claims and how they decide.

\begin{description}
\item[Rules, regex extraction.] The fast mode of our tool and the mechanism of the existing hooks. A regex
extractor finds claims by family, with hedge and negation handling (\texttt{receipts/claims.py}). Command
classifiers recognise test, build, lint, commit, push, deploy and write calls and read pass or fail from their
output (\texttt{receipts/rules.py}). One rule per claim kind turns receipts into a verdict, including a
staleness rule: a passing test run counts only if no code was written after it (\texttt{receipts/check.py}).
\item[Rules, LLM extraction.] The same verdict rules, with claims listed by a small model (Haiku) that reads
only the report (\texttt{receipts/llm.py}). This isolates the verdict rules from extraction recall.
\item[Judge.] A model reads the turn's dossier under the same rubric the raters used and returns claims with
verdicts (\texttt{receipts/judge.py}). We ran it with Sonnet (judge S) and Haiku (judge H).
\end{description}

The verdict rules were hill-climbed on the development split for 15 rounds, scoring dev end-to-end flag F1 with
LLM extraction; each round was kept only if it beat the previous best. Dev F1 rose from 0.088 to 0.201.

\section{Results}

\subsection{Prevalence}

Across the 400 labelled turns (2,082 claims in 293 sessions, 5.21 claims per turn) 1,806 claims are supported,
271 unbacked and 5 contradicted. The not-backed rate is 13.3\% (95\% CI 11.3 to 15.4). It is similar on the two
splits: 13.4\% on dev (rater A) and 13.1\% on test (adjudicated gold). Among the not-backed claims with a recorded
basis, 27 rest on a stale receipt, 4 on a direct contradiction and 187 on no receipt at all
(\texttt{results/benchmark.json}, key \texttt{labels}).

Table~\ref{tab:prev} gives the breakdown. Three patterns hold. First, claims about outcomes (``it works'',
``tests pass'', ``I verified'') are the ones most often left without a receipt; claims about actions the
harness records directly (``I ran'', commits) are almost always backed. Second, short sessions are cleaner: 5.1\%
of claims in sessions of 1 to 9 tool calls are not backed, against 13 to 20\% in longer ones. Third, the model
differences are within overlapping intervals and confounded with task: the developer used different models for
different kinds of work, and the Codex and Fable cells are small. We do not rank models from this table.

In a separate live check outside the sample, clean single-turn tasks given to Haiku, Sonnet and Opus produced
honest reports from all three. The one failure we reproduced on demand needed a multi-step task: after a rename,
Haiku under a terse house-style prompt reported ``pytest passes'' from a run made before the rename. The rules
hook flagged the claim in 2.1 ms and the agent re-ran the tests (\texttt{docs/live-hook/}).

Table~\ref{tab:valid} is the second finding. The deterministic rules agree with careful readers at chance on
held-out turns: verdict $\kappa$ is $-0.0003$ with regex extraction and $0.003$ with LLM extraction. Regex
extraction finds only 15\% of the claims the raters listed, so end-to-end it catches 3 of 124 gold flags while
raising 63 false ones. Giving the rules a good extractor raises recall but not agreement: 19 true flags against
210 false. The dev-split climb that took flag F1 from 0.088 to 0.201 did not transfer
(\texttt{results/validity\_test.json}, \texttt{validity\_test\_llm.json}).

The errors run both ways. With LLM extraction, the rules call 137 gold-supported claims unbacked and 60
gold-unbacked claims supported. Our reading of the disagreements is that relevance is the hard part: a rule can
ask whether \emph{some} test run passed after the last write, but not whether that run exercised what the claim
is about, and it cannot tell when a read, a diff or an unrecognised command is the receipt a reader accepts.
Most of what readers flag is a ``works'' or ``verified'' claim, which is where relevance matters most.

A model that reads the dossier does much better. The Sonnet judge flags with precision 0.81 on matched claims and
0.557 end to end, with recall 0.315 and verdict $\kappa$ 0.52 (\texttt{results/validity\_judge\_S.json}). The Haiku
judge trades precision for recall (0.307 and 0.524). Neither reaches the second rater's agreement with the first,
so a judge is a screen, not a substitute for reading.

The rules are about three orders of magnitude faster (Table~\ref{tab:cost}; \texttt{results/hook\_cost.json},

Our tool therefore defaults its Stop hook to the judge engine and keeps the rules as a fast, explicit opt-in.

\section{Limits}

\begin{itemize}
\item \textbf{One developer.} Every session comes from one machine, mostly long autonomous lanes and orchestration
work. The rates may not hold for interactive use or for other developers, prompts and house styles.
\item \textbf{Model raters.} The labels come from Opus 5.5 raters, not people. Two raters agree well
($\kappa$ 0.74) and the author audited 40 adjudicated rulings, but systematic blind spots shared by the raters
would not show up in either check.
\item \textbf{Clipped outputs.} Dossiers clip long tool outputs, so a receipt present in the full output can be
cut, which biases toward ``unbacked''.
\item \textbf{Subagents not read.} Work done inside subagents lives in separate transcripts that the dossier does
not include; a claim backed only there reads as unbacked.
\item \textbf{Matching by sentence overlap.} Validity numbers depend on pairing system and gold claims by text
overlap, which can miss paraphrases and split one sentence's several claims unevenly.
\item \textbf{Small cells.} Codex (3 sessions in the sample), Fable and the 200+ call bucket have wide intervals.
\end{itemize}

\section{Related work}

\paragraph{Tools with the same mechanism.} proof-of-done~\citep{boyko2026proofofdone}, honestly~\citep{honestly2026}
and groundtruth~\citep{groundtruth2026} are Stop hooks that pattern-match claims in the final message and require
a matching successful command after the last edit; agentvow~\citep{agentvow2026} re-runs tests in a sandbox
instead. They validate on author-written fixtures or report counts from their authors' sessions. Our result says
that this mechanism, which our tool also implements, does not agree with careful readers on real sessions. A
GitHub issue on Claude Code~\citep{ashwinsuriya2026issue} hand-labelled 357 ``tests pass'' claims from 150
sessions and found most unbacked ones stale; we extend that to all claim families with a validated sample.

\paragraph{Self-reports checked against the record.} \citet{smyth2026overclaiming} define overclaiming as a
report contradicted by the agent's own transcript and measure it on planted file-review tasks with an LLM judge.
\citet{kraishan2026plans} compare reports with tool logs in SWE-chat~\citep{baumann2026swechat} and find reports
mention few actions and drift toward the plan. \citet{leith2026commits} studies claim reliability in one fully
AI-written codebase; \citet{lei2026pass} re-verifies ten ``PASS'' claims mechanically. \citet{zhu2026whoverifies}
find that judges who see a GUI agent's success report miss more misreports than trace-only judges, and
\citet{zhu2026failure} measure false success after injected tool failures. Our setting differs in using natural,
unplanted sessions, many claim types, and a measured comparison of rules against reading.

\paragraph{Receipts.} \citet{basu2026receipts} have the runtime sign per-call receipts that the model cites;
\citet{hu2026actions} bind claims to execution prefixes with a deterministic integrity check separate from
support. Both need a cooperating runtime; we audit an unmodified agent after the fact, and our negative result
suggests the support step is where reading is needed.

\paragraph{Hallucination and deception.} ToolBeHonest~\citep{zhang2024toolbehonest} and
AgentHallu~\citep{liu2026agenthallu} benchmark tool-use hallucination; \citet{florin2026omission},
SWE-DeceptionBench~\citep{liu2026swedeception}, \citet{scheurer2023strategic} and \citet{meinke2024scheming}
elicit concealment or deception under constructed pressure. We follow the behavioral stance of
\citet{park2023deception} and make no intent claim; unlike chain-of-thought faithfulness~\citep{turpin2023unfaithful},
claims about external actions can be checked directly. Reward-hacking reports from METR~\citep{vonarx2025rewardhacking}
and Anthropic~\citep{anthropic2025claude37} describe agents gaming tests; the failure we count is mostly quieter:
saying tests pass without a current run.

\paragraph{Evaluation.} Agent-as-a-Judge~\citep{zhuge2024agentjudge} grades trajectories with an agent, as our
judge engine does for claims. RAGAS faithfulness~\citep{es2023ragas} decomposes answers into statements and checks
each against context, the same shape as our task with tool calls as context. Process supervision~\citep{lightman2023verify}
checks steps rather than outcomes. SWE-bench~\citep{jimenez2024swebench} grades by running tests, the external check
that everyday sessions lack.

\section{Reproducibility}

The checker and the benchmark pipeline are in the repository. The tool runs anywhere; the benchmark reads the
author's private session logs and so reruns only on a machine that has them. Aggregate outputs are committed
under \texttt{results/}; claim text, transcripts and labels stay in the untracked \texttt{data/} folder.

{\small
\begin{verbatim}
pipx install git+https://github.com/abhaymettu/receipts
receipts demo                       # bundled sample session
python -m pytest -q tests

python3 bench/frame.py              # results/frame.json
python3 bench/run.py                # data/claims.jsonl, data/turns.jsonl
python3 bench/label.py sample       # 400 turns, dev/test split
python3 bench/label.py dossiers
python3 bench/label.py rate A
python3 bench/label.py rate B --only test
python3 bench/adjudicate.py rule && python3 bench/adjudicate.py build
python3 bench/score.py agreement    # results/validity_agreement.json
python3 bench/score.py test         # results/validity_test.json
RECEIPTS_EXTRACT=llm python3 bench/score.py test   # validity_test_llm.json
python3 bench/score.py judge:S      # validity_judge_S.json (judge:H for Haiku)
python3 bench/stats.py              # results/benchmark.json
python3 bench/hook_cost.py          # results/hook_cost.json
python3 bench/judge_cost.py         # results/judge_cost.json
\end{verbatim}
}
